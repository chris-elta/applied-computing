Whether your code is limited by arithmetic or by memory traffic is not a matter of
opinion. It follows from one ratio:

```
arithmetic intensity = FLOPs performed / bytes moved
```

Plot achievable performance against that ratio and you get a roof with two parts. The
**sloped section** is the bandwidth limit — at low intensity you can only compute as
fast as data arrives. The **flat section** is the compute limit — past a crossover
point, memory keeps up and your peak FLOP rate binds instead.

## Why it settles arguments

Locate your kernel on that graph and the optimisation question answers itself:

- **Under the slope** — memory bound. Improve reuse: block for cache, change layout,
  compress. Faster arithmetic is wasted effort.
- **Under the flat part** — compute bound. Now vectorisation, better instruction
  selection, and lower-precision arithmetic pay off.
- **Near the roof** — you are close to what the hardware can do. Further gains need a
  different algorithm, not a better implementation of this one.

Most real code sits well under the sloped section, which is the same conclusion the
memory hierarchy pushed us towards: **moving data, not computing on it, is usually what
costs you.** The roofline just makes it quantitative.
