Parallelism is bounded by the part of the program that refuses to be parallel. If a
fraction `p` of the runtime can be spread across `N` workers and the rest cannot:

```
S = 1 / ((1 - p) + p/N)
```

Let `N` grow without limit and the `p/N` term vanishes, leaving `S = 1 / (1 - p)`. The
speedup ceiling depends only on the **serial fraction** — the part you didn't
parallelise.

## Why this is worth knowing before you start

The numbers are brutal in a way intuition isn't. A program that is 95% parallel — which
already sounds like a triumph — caps out at 20×, no matter whether you throw 64 cores or
64,000 at it. At 99% parallel the ceiling is 100×.

So the useful question is never "how do I spread this across more cores". It's **"what
is my serial fraction, and can I shrink it"**. An hour spent removing a lock that
serialises 5% of the runtime can be worth more than any amount of scaling out.

> The same reasoning applies well beyond threads. Any optimisation that speeds up only
> part of a system is governed by this: fix the part that dominates, or accept the
> ceiling that the rest imposes.
