A permutation test relies on shuffling. If some orderings come up more often than others, the
shuffled data is not a fair picture of "no effect", and the p-value is wrong. Slide 28 shows
that writing a fair shuffle is *surprisingly subtle*.

## Two candidates

Both start with `a[i] = i` and then walk along the array swapping:

| | step `i` swaps `a[i]` with |
| --- | --- |
| algorithm 1 | `a[Random[i, n]]`: a position from `i` to the end |
| algorithm 2 | `a[Random[1, n]]`: any position at all |

They differ in one index and look equally random. They are not.

## The experiment

Slide 29 shuffles four items a million times with each algorithm and counts how often each of
the `4! = 24` orderings appears. A fair shuffle should give each one about
`1,000,000 / 24 ≈ 41,667`.

| | how the 24 counts look | standard deviation of counts |
| --- | --- | --- |
| algorithm 1 | all near 41,600, a flat line | 166.1 |
| algorithm 2 | from about 78,000 down to about 16,000 | 20,932.9 |

Algorithm 1 is **uniform**. Its small variation is ordinary randomness. Algorithm 2 favours
some orderings nearly five times as much as others.

## Why, by counting

Count the equally likely ways each algorithm can run.

**Algorithm 1** has `n` choices at step 1, then `n − 1`, then `n − 2`, down to 2. That is
`n × (n−1) × … × 2 = n!` runs. There are `n!` orderings, and each run gives a different one,
so every ordering appears exactly once. It is uniform.

This makes sense position by position. Step 1 picks the item for position 1 from all `n`. Step
2 picks position 2 from the `n − 1` remaining, and so on. That is how you would deal cards by
hand.

**Algorithm 2** has `n` choices at each of its `n − 1` steps, so `nⁿ⁻¹` runs. For `n = 3`, that
is `3² = 9` runs spread over `3! = 6` orderings. Nine cannot be split evenly six ways, so some
orderings must come up more often. For `n = 4`, the 64 runs cannot be split evenly 24 ways
either.

## Why, in words

The slides give the argument without the counting. **Algorithm 1 picks a random item for the
first position, then leaves it alone and recurs** on the rest. Each position is settled once,
fairly, and never touched again. So the result is a random permutation by construction.

**Algorithm 2 never leaves a position alone.** A later step can reach back and swap a new item
into a position already settled. The slide describes this as giving *subsequent elements a better
chance to end up first*. Counting all 64 runs for `n = 4` shows the bias is lopsided rather than
simply favouring later items:

| item | runs that end with it first | fair share |
| --- | --- | --- |
| 1 | 16 | 16 |
| 2 | 21 | 16 |
| 3 | 18 | 16 |
| 4 | 9 | 16 |

Item 2 lands first a third more often than it should, and item 4 only a little over half as
often. Across whole orderings, the rarest comes from 1 of the 64 runs and the commonest from 5.
Over a million shuffles that is about 15,600 against 78,100, which matches the two ends of the
red line on slide 29.

Algorithm 1 is known as the **Fisher-Yates shuffle**, and it is what library shuffle functions
use.

## The lesson

The slide's moral: random generation can be very subtle. Code that looks random is not
necessarily uniform. A shuffle can produce every ordering and
still be biased. The slides' test is the one to reuse: generate many samples, count, and
compare the counts with what uniform would give.

> Algorithm 1, swapping each position with a random one from the rest, gives every ordering
> exactly one path. Use a library shuffle, and when in doubt, count the outcomes.
