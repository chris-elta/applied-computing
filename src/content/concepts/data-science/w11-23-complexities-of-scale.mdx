The previous concept said distributed work is harder than parallel work. Slide 19 says how
the difficulty grows: **rapidly, with the number of machines**.

| machines | what the work is |
| --- | --- |
| One | keep the cores of your box busy |
| Two | manually run programs on a few boxes |
| Many | employ a system like MapReduce to manage the machines efficiently |

With one machine the problem is using it fully. With a few, you can log in to each, start a
program and copy the results back by hand. With hundreds, doing it by hand is impossible, and
you need software whose whole purpose is to hand out work, track it and collect results.
These are three different kinds of work.

## The gathering analogy

Slide 20 makes the same point with people.

| size of gathering | what changes |
| --- | --- |
| 1 person | easy to arrange |
| more than 2 | coordination |
| more than 10 | requires a leader in charge |
| more than 100 | requires a fixed menu |
| more than 1,000 | no one knows many people |
| more than 10,000 | too few hotels for most cities |
| more than 100,000 | someone will die that day |

Each row brings a problem the previous size did not have. Past 10 you need a coordinator.
Past 100 you can no longer treat individuals differently, hence the fixed menu: standardise
the work. Past 1,000 no participant knows the whole. Past 10,000 you hit the limits of the
infrastructure.

The last row matters most. Among 100,000 people on an ordinary day, a death is a statistical
expectation. Nobody did anything wrong. An event that is vanishingly rare for one person
becomes near-certain when there are enough people.

Replace people with machines and "die" with "fail". A disk that fails once in several years
is reliable. Ten thousand of them produce failures daily. At scale, **failure is a normal
operating condition**.

## A real case

Slide 21 gives figures for training GPT-4.

| | |
| --- | --- |
| GPUs | 25,000 NVIDIA A100 |
| training time | 90–100 days |
| training cost | $63 million, not including researcher salaries |
| energy | an estimated 50 GWh |
| data set | 13 trillion tokens |
| floating point operations | 2.15e25 |
| batch size | increased over time, eventually reaching 60 million tokens |

The slide's closing remark ties it to the analogy: **recovering from machines dying had to
be an important aspect of the training architecture**. A run on 25,000 GPUs for three months
will lose machines. If one failure meant starting again, the job would never finish. The
architecture has to notice a dead machine, redo its share and continue.

> Scale changes the kind of problem you have, not only its size. Beyond a few machines you
> need a system to coordinate them, and beyond many, something is always broken, so the
> system must expect failure and recover.
