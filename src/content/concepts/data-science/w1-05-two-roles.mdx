A product needs more than one kind of person. The slides list the cast: data engineers,
domain specialists, operators, a business team, project managers, designers and UI experts,
safety and security specialists, lawyers, social scientists and more. Two roles sit closest
to the model, and the lecture sets them side by side.

| | Data scientist | Software engineer |
| --- | --- | --- |
| Data | Often a fixed dataset for training and evaluation | Large amounts of live data, which the solution must scale to |
| Goal | Accuracy | A product: performance, stability, release time |
| Working style | Prototyping, often in Jupyter notebooks | Maintaining, evolving and extending over long periods |
| Expertise | Modelling techniques and feature engineering | Detecting and handling mistakes, preferably automatically |
| Judged by | Accuracy on evaluation data | Customer satisfaction |
| Often ignored | Model size, updateability, implementation stability | Requirements for security, safety and fairness are considered |

## Where friction comes from

The slides pose two open questions to the room: *likely collaboration challenges?* and
*what might each role focus on?* The table answers them without being asked. If one person
optimises for accuracy on a fixed set while the other worries about stability and updates,
each will experience the other's default behaviour as an obstacle.

Neither view is wrong. A model that cannot be deployed is not a product; a product built
around a poor model is not useful. Trouble starts when each side assumes the other's concerns
are the same as its own.

> When people on the same team disagree, check first whether they are optimising for
> different things.
