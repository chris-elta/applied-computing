Map and reduce are the two functions you must write. Slide 29 adds two more primitives.
They explain how the framework keeps its promise and how to make a job cheaper.

## Partition: which reducer gets a key?

The promise was that all values with the same key reach the same reducer. With several
reducers and many mappers on different machines, how does each mapper know where to send a
key without asking anyone?

```
partition (k′, number of partitions)  →  partition for k′
```

The slide says it is often a simple hash of the key: `hash(k′) mod n`. A hash turns the key
into a number, and the remainder after dividing by the number of reducers `n` picks one.
The slide's table uses three reducers.

| key | `hash(key)` | `hash(key) mod 3` | goes to |
| --- | --- | --- | --- |
| apple | 145 | 1 | Reducer 1 |
| banana | 211 | 1 | Reducer 1 |
| pear | 84 | 0 | Reducer 0 |

Check one: `145 = 48 × 3 + 1`, so the remainder is 1.

Every mapper computes the same hash for `apple`, so every mapper sends `apple` to Reducer 1,
with no coordination. That is the mechanism behind the guarantee. Different keys may share a
reducer, as apple and banana do here, and that is fine. What must never happen is one key
going to two reducers.

The slide gives the purpose: partitioning divides up the key space for parallel reduce
operations.

## Combine: summarise before sending

In word count, a mapper that sees `the` a thousand times emits a thousand copies of
`(the, 1)`, and every one crosses the network. The network is the slow, expensive part of a
distributed system.

```
combine (k′, [v′])  →  [(k′, v″)]
```

The slide describes combiners as **mini-reducers that run in memory after the map phase**,
used as an optimisation to **reduce network traffic**. A combiner does on one mapper's
output what the reducer will later do on everyone's.

Slide 30 reruns word count with one. The second document is "the fox ate the mouse".

| | this mapper sends for `the` |
| --- | --- |
| without combiner | `(the, 1)` and `(the, 1)` |
| with combiner | `(the, 2)` |

The reducer for `the` now receives `[1, 2]` where before it received `[1, 1, 1]`. The sum is
3 either way, and the final output on the slide is unchanged.

## When a combiner is safe

A combiner only sees one mapper's share. The final answer must come out the same whether
values are summarised early in pieces or all at once. Addition has that property: adding
some numbers first and the rest later gives the same total. An average does not, since the
average of several averages is generally not the overall average. For word count, the
combiner can be the same summing function as the reducer.

> The partitioner sends each key to a reducer chosen by `hash(key) mod n`, which is how
> equal keys always meet. A combiner summarises a mapper's output locally to cut network
> traffic, and is safe when early partial summaries do not change the final result.
