In traditional software engineering you **specify what to do and how to test it**. You write
the rule, then write a check that the rule holds. Machine-learning components break that
loop in two ways.

## No written specification

Models are usually **black boxes**. That may be justified by their complexity, but it means
you cannot read a rule off the system.

Even when you do try to state a specification — for example inside an LLM prompt — it is
unclear whether the model will follow it.

## The specification comes from data

Instead of a programmer's rules, a model gets its "specs" from **data**, and the larger the
dataset, the better. The slide describes this as a shift:

| Traditional software | Machine learning |
| --- | --- |
| Deductive reasoning: apply logic rules | Inductive reasoning: generalise from observations |
| Behaviour follows from the rules written | Behaviour follows from the data seen |

The dependence on large datasets is also what **causes scalability issues** — storing,
cleaning and processing data becomes part of the system's job.

## Consequences

Two things follow that the next slides develop:

- Without a spec, you cannot say exactly what a correct output is. See the next concept.
- The behaviour of the system reflects the data it learned from, so a change in the data can
  change the behaviour, even if no code changed.

> With ML, the data is part of the program.
