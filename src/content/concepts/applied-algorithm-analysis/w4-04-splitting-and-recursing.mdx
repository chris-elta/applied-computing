Take any pivot `v` and split `S` into three piles by comparison, in one linear pass:

- `S_L` — elements smaller than `v`;
- `S_v` — elements equal to `v`, duplicates included;
- `S_R` — elements greater than `v`.

On `S = [2, 36, 5, 21, 8, 13, 11, 20, 5, 4, 1]` with `v = 5`: `S_L = [2, 4, 1]` (3 of 11),
`S_v = [5, 5]` (2 of 11), `S_R = [36, 21, 8, 13, 11, 20]` (6 of 11) — every one of the 11
elements lands in exactly one pile.

## Which pile do you recurse into?

```
selection(S, k) = selection(S_L, k)                     if k ≤ ∣S_L∣
                = v                                       if ∣S_L∣ < k ≤ ∣S_L∣+∣S_v∣
                = selection(S_R, k − ∣S_L∣ − ∣S_v∣)       if k > ∣S_L∣+∣S_v∣
```

Three things make this work:

- `S_L`, `S_v` and `S_R` are all computed from `S` in one linear pass;
- recursion is applied to **one** of the three sublists only, never two;
- the split shrinks the problem from `∣S∣` elements to at most `max{∣S_L∣, ∣S_R∣}`.

That last point is the structural payoff of module 3's "recurse into one side" observation: a
recursive call on `S_L` or `S_R` is strictly smaller than `S`, so the recursion makes real
progress every time it fires — unless `v` itself is the answer, in which case there's no
recursion left to do.

Contrast this with mergesort, where `a = 2`. Here `a = 1`: there is exactly one recursive
call, which is why the running time will come out linear rather than `O(n log n)` once the
master theorem is applied.
