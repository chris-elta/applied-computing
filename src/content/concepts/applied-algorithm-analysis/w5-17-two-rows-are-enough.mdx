The edit-distance table has `(m + 1)(n + 1)` cells. For two short words that is nothing. For
two documents of a million characters each it is about a trillion cells — far too much to
hold in memory, long before the running time becomes the problem.

## Look at what a cell reads

```
E(i, j) = min{ 1 + E(i−1, j),  1 + E(i, j−1),  diff(i, j) + E(i−1, j−1) }
```

Three cells: `E(i−1, j)` and `E(i−1, j−1)` are in the row above, and `E(i, j−1)` is in the
current row. Nothing from two rows up, or any earlier row, is ever read.

So when row `i` is being filled, rows 0 to `i − 2` are dead weight. Keep two rows — the one
above and the one being written — and throw the rest away as you go.

| | Full table | Two rows |
| --- | --- | --- |
| Memory | `O(mn)` | `O(n)` |
| Running time | `O(mn)` | `O(mn)` — every cell is still computed |
| Final distance | exact | exact |

## The same trick you have already seen

In the tabulation concept, `fib2` kept an array of `n` entries but only ever read the last
two, and that is how the array collapsed to two variables. This is the same move with a
bigger unit: there it was a number, here it is a row.

The general test is to look at the dependency arrows. If every arrow into a cell comes from
a narrow band just behind it, only that band needs to be stored.

## What you give up

The next concept recovers the actual alignment — which letters were substituted, inserted or
deleted — by walking backwards from the bottom-right cell to the top-left. That walk visits
a cell in every row. With only two rows kept, there is nothing to walk through.

So the choice is:

- **you need only the distance** → two rows, `O(n)` memory;
- **you need the alignment too** → the whole table, or pointers stored as you go.

> Storing less is possible when each cell only looks a short way back. But a table that has
> forgotten its history can tell you the cost of the best solution and not what the solution
> is.
