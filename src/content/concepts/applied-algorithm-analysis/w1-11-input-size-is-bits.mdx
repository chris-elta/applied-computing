Everything so far assumed basic arithmetic takes one step. That is false, and it is about to
matter: cryptography uses numbers with hundreds of digits, where one addition is emphatically
not one step.

To price arithmetic honestly we first need to agree what "input size" means.

## How long is a number?

Take one million.

- Its **value** is 1,000,000. Call that `N`.
- Its **length written down** is 7 decimal digits, about 20 bits. Call that `n`.

**Input size is always the second one** — how much you must write down to state the input,
not how big it is.

In general, writing `N` in base `b` takes `⌈log_b(N+1)⌉` digits: `log_b N` counts how many
digit positions you need, and `⌈ ⌉` rounds up, since you cannot have 6.9 digits.

The base only matters by a constant — `log_b N = log₂ N / log₂ b` — and constants are what
`Θ` discards. So:

> **`n` = the number of bits ≈ `log₂ N`.**

## Why this changes everything

An algorithm handed `N` receives an input of length `log N`, not `N`. Turn that round and it
bites: a loop counting from 1 to `N` takes time proportional to `2ⁿ` in its input size. **A
loop that looks linear in the value is exponential in the input.**

## Addition, priced honestly

```
  1 1 1 1    carries
    1 1 0 1  (13)
  + 1 0 1 1  (11)
  ───────────
  1 1 0 0 0  (24)
```

Column addition works because of one fact, true in any base `b ≥ 2`: the sum of any three
single digits is at most two digits. Three is the right number — the two digits plus an
incoming carry — and it caps the outgoing carry at 1.

So each column is fixed, small work: three bits in, one bit and one carry out. With `n`
columns, addition costs **`O(n)`**.

## And you cannot do better

To produce a correct sum you must at least *read* both numbers, which is `n` operations. So
every possible addition algorithm costs at least `Ω(n)`.

Upper and lower bounds meet: addition is `Θ(n)`, and the question is closed — a rare and
satisfying position.
