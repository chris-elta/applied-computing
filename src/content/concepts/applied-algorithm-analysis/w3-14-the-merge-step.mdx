Everything mergesort does is here.

```
function merge(x[1…k], y[1…l])
  if k = 0: return y[1…l]
  if l = 0: return x[1…k]
  if x[1] ≤ y[1]:
    return x[1] ∘ merge(x[2…k], y[1…l])
  else:
    return y[1] ∘ merge(x[1…k], y[2…l])
```

Compare the two fronts, emit the smaller, repeat. The two base cases are the stopping rule:
when one list is empty there is nothing left to compare, so the other list *is* the answer.

Each recursive call removes one element and does a single comparison, so the running time is
`O(k + l)` — linear in the output.

## Traced

Merging `[2, 3, 5, 10]` with `[1, 6, 7, 13]`:

| compare | emit |
| --- | --- |
| 2 vs 1 | 1 |
| 2 vs 6 | 2 |
| 3 vs 6 | 3 |
| 5 vs 6 | 5 |
| 10 vs 6 | 6 |
| 10 vs 7 | 7 |
| 10 vs 13 | 10 |
| — | 13 |

**Eight elements written, seven comparisons.** The last element is free: by then `x` is
empty, so 13 is copied across with nothing to compare it against.

That generalises. Every comparison writes exactly one element and shortens one input by one,
so `k + l` elements need at most `k + l − 1` comparisons. With `k = l = 4` the bound is 7,
and 7 is what this took.

The *best* case is 4 — when every element of `x` is below every element of `y`, so `x` empties
and the rest of `y` is copied untouched. Between 4 and 7, and both ends are linear, which is
all the analysis needs.

## The tree of merges

Slide 36 shows the whole thing for eight numbers: 8 lists of 1, then 4 merges of 2 items,
then 2 merges of 4, then 1 merge of 8. Three levels of merging, and `log₂8 = 3`.

Every level moves all 8 items, so every level costs `O(n)` — which is the balanced case made
visible.

```
T(n) = 2T(n/2) + O(n)   ⟹   O(n log n)
```

> Read that tree bottom-up and mergesort becomes an **iterative** algorithm: merge adjacent
> pairs, then adjacent pairs of pairs, and so on. No recursion required — the recursion was
> only ever a way of describing the order.
