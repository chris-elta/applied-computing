Three things to carry forward, and one habit.

## 1 · The algorithm decides what is computable, not the machine

One problem, three algorithms, exponential down to linear — with the hardware never changing.
`fib1` multiplies its work by `φ ≈ 1.618` per extra `n`, so a machine twice as fast buys
about **1.4 more inputs**. `fib2` reaches `n = 200` in 199 additions on anything.

That gap is not an optimisation. It is the difference between possible and impossible.

## 2 · Asymptotic notation reports the shape, not the number

**Suppress constant factors and lower-order terms** — constants because they describe your
machine, lower-order terms because they stop mattering.

| | reads as | means |
| --- | --- | --- |
| `O` | `≤` | grows no faster than |
| `Ω` | `≥` | grows at least as fast as |
| `Θ` | `=` | grows at the same rate as |
| `o` | strict `<` | grows strictly slower than |

Two things to keep straight: a claim needs **witnesses** (an actual `c` and `n₀`) to be
proved rather than asserted; and bound-tightness is a *separate axis* from which case you
mean.

## 3 · For numbers, input size is bits

`N` is a value; `n ≈ log₂ N` is its length. Forgetting that is what makes an innocent loop
over `1…N` secretly exponential. Once you count bits, arithmetic stops being free:

| on `n`-bit numbers | cost |
| --- | --- |
| addition | `O(n)` |
| multiplication | `O(n²)` |
| division and mod | `O(n²)` |
| modular exponentiation | `O(n³)` |
| gcd, by Euclid | `O(n³)` |

## The habit: rounds × cost per round

The last two rows were derived the same way, with nothing clever:

- **Fast exponentiation** — exponent halves each call → `n` rounds; each is one modular
  multiplication at `O(n²)`.
- **Euclid** — larger value halves every two rounds → `2n` rounds; each is one division at
  `O(n²)`.

Find the round count, find the per-round cost, multiply. That is the most reusable thing in
this week's material, and what next week's recurrences generalise.
