Addition came out at `Θ(n)` and optimal. Multiplication is where the price starts to hurt.

The long multiplication you learned in decimal works in any base, and binary makes it
unusually simple:

```
    1 1 0 1     (13)
  × 1 0 1 1     (11)
  ───────────
    1 1 0 1     13 × 1
  1 1 0 1 ·     13 × 1, shifted once
0 0 0 0 · ·     13 × 0, shifted twice
1 1 0 1 · · ·   13 × 1, shifted three times
───────────────
1 0 0 0 1 1 1 1 (143)
```

Each row is a **partial product**: the top number times one digit of the bottom number,
shifted into place. In decimal that needs a real multiplication per row. In binary the digit
is 0 or 1, so every row is either **nothing** or **a copy of `x`** — and shifting is free, you
just append a zero.

(Check the third row is all zeros, because bit 2 of `11 = 1011₂` is 0.)

## So what does it cost?

The multiplications are free. The **additions** are not.

There are `n` partial products, each up to `2n` bits long, and they have to be added
together — `n` additions, each at the `Θ(n)` price established on the previous page.

> `n` rows × `O(n)` per row = **`O(n²)`**

Changing base does not help. Adding the rows in a different order does not help — there are
still `n` of them.

## The first non-linear operation

This is worth marking. Addition was linear in the digits and provably optimal. Multiplication
is **quadratic**, and that is the first time a basic arithmetic operation has cost more than
a single pass over its input.

Whether `O(n²)` is the *best possible* for multiplication is a genuinely different question,
and a much harder one. The next two pages show two methods that look nothing like this one
and cost exactly the same — which is a hint that beating it needs a new idea rather than a
rearrangement.
