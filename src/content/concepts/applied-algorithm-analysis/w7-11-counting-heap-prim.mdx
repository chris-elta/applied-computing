Each heap operation costs `O(log n)`, because the heap has `O(log n)` levels. Extract-min
moves an entry down, decrease-key moves one up, and each does at most one swap per level.
What remains is to count how many times each happens.

## Count over the whole run, not per round

Do not ask "how much can one round cost?" and multiply by `n − 1`. Ask how many times each
operation happens in the entire run.

| Operation | How many times | Total cost |
| --- | --- | --- |
| extract-min | `n − 1`, once for each vertex after the start | `O(n log n)` |
| decrease-key | at most `m`, only when a cheaper connection appears | `O(m log n)` |
| check a neighbour | `2m`, each vertex's list is read once, when it is extracted | `O(m)` |
| heap setup | once | `O(n)` |

Locating an entry through the position table costs `O(1)` each time and is already covered by
the decrease-key line. The first scan, of the start vertex `s`, is one of the `2m` checks.

## Why "each list once"

A vertex's list is scanned when the vertex is extracted, and a vertex is extracted only once.
It never re-enters the heap. So across the whole run, Prim reads every list exactly once,
`2m` entries in total. The basic version reread every list on every round.

That is also why decrease-key happens at most `m` times. An edge `(v, w)` appears in two
lists. Whichever endpoint is extracted first, say `v`, reads the edge while `w` is still
outside `X`, and that read may lower `key[w]`. When `w` is extracted later, `v` is already in
`X`, so the entry is skipped. Each edge can trigger one decrease-key at most.

## Add it up

`O(n + m + n log n + m log n) = O((n + m) log n)`.

For `n ≥ 2`, `log n ≥ 1`, so the `log n` terms are at least as large as the linear ones, and
the linear terms disappear into them. For a connected graph `n ≤ m + 1`, and this is often
written `O(m log n)`.

## Against the basic version

| Implementation | Running time | 1,000 vertices, 100,000 edges |
| --- | --- | --- |
| rescan every round | `O(mn)` | about `2 × 10⁸` entry reads |
| indexed heap | `O((n + m) log n)` | about `10⁶` steps |

The factor of about 200 comes from not rereading edges that have not changed. The heap does
not do the scans themselves any faster.

> Count each operation over the whole run. Lists are scanned once each, so there are `2m`
> checks, at most `m` decrease-keys and `n − 1` extract-mins, which gives
> `O((n + m) log n)`.
