Every cost so far has assumed that basic arithmetic takes one step. Adding two numbers: one
step. That has been harmless, because the numbers were small.

This is the lecture where it stops. Cryptography routinely uses numbers with hundreds of
digits, and there one addition is emphatically not one step. To price arithmetic honestly, we
first have to agree what "the size of the input" even means.

## How long is a number?

Take `N = 1000`. The same number, written three ways:

| base | written | length |
| --- | --- | --- |
| 10 | `1000` | 4 digits |
| 2 | `1111101000` | 10 bits |
| 16 | `3E8` | 3 digits |

In general, writing `N` in base `b` takes `⌈log_b(N+1)⌉` digits — `log_b N` counts the digit
positions you need, and `⌈ ⌉` rounds up, since there is no such thing as 6.9 digits.

Does the base matter? Only by a constant: `log_b N = log₂ N / log₂ b`. Constant factors are
exactly what `Θ` discards, so up to `Θ` the answer is unambiguous:

> **`n` = the number of bits ≈ `log₂ N`.**

## Why that changes everything

An algorithm handed `N` is handed a **row of digits**, not a quantity. It receives an input
of length `log N`, not of length `N`.

Turn that around and it bites. Take a loop that counts from 1 up to `N`:

- `N = 1000` is 10 bits of input, and the loop runs 1000 times — that is `2¹⁰`.
- Add **one bit** to the input and it becomes 11 bits, `N = 2000`, and the loop runs twice as
  long.

One extra character of input, twice the work. That is exponential growth in `n`, dressed up
to look linear in `N`. The animated figure on slide 7 is worth running twice: watch the input
row grow by a single cell while the work bar doubles.

> **Input size is bits, not value.** Every cost in this week is measured in the digits of the
> numbers involved — never in how big they are.
