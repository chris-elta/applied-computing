Selection generalises the median. Instead of fixing `k = ⌊∣S∣/2⌋`, let `k` be any rank:

> **Selection.** *Input:* a list of numbers `S`; an integer `k`. *Output:* the `k`-th smallest
> element of `S`.

Two boundary cases are already-familiar algorithms in disguise: `k = 1` asks for the minimum
of `S`, and `k = ∣S∣` asks for the maximum — both obviously solvable in one linear pass, no
sorting required. `k = ⌊∣S∣/2⌋` is the median from the previous concept, and it is the hard
case: there is no one-pass trick for reading off the middle of an unsorted list. The rest of
this module builds an algorithm that handles every `k`, median included, in the same amount of
time a single linear pass takes.

## How to solve it?

The obvious approach: sort the array, then read off position `k`.

```
O(n log n)  [mergesort]  +  O(1)  [index]  =  O(n log n)
```

That works, but it is worth being precise about *why* it feels wasteful. Sorting the whole
array does not just answer the question for the `k` you asked about — it produces the correct
answer for every value of `k` from 1 to `∣S∣` simultaneously, since the entire order is now
sitting there. If the question only ever asks for one rank, `O(n log n)` is the price of
computing 999,999 answers nobody wanted, for an input of size a million.

That is the opening this module works: **can selection be solved in less time than sorting,
by refusing to produce the answers nobody asked for?**
