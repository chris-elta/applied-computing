The plain adjacency list — a list of neighbor names per vertex — is all that graph search
needs. Some applications want more: weights or other data on each edge, or the ability to
delete an edge quickly. Here is one richer layout, and what it takes to make deletion
constant time.

## One implementation, four parts

Using the same four-vertex graph, with edges `e₁₂, e₂₃, e₂₄, e₃₄`:

| part | example |
| --- | --- |
| 1. a collection of all vertices | 1, 2, 3, 4 |
| 2. a collection of all edges, one record each | `e₁₂, e₂₃, e₂₄, e₃₄` |
| 3. each edge points to its endpoints | `e₂₄` points to vertex 2 and vertex 4 |
| 4. each vertex points to its incident edges | vertex 2 → `e₁₂, e₂₃, e₂₄`; vertex 4 → `e₂₄, e₃₄` |

You need all four. Note that `e₂₄` is one record, and vertex 2 and vertex 4 both hold a
reference to it. An "edge record" is just a record with fields; nothing here needs objects.

## Finding a neighbor

To list vertex 2's neighbors, follow each of its edge references and take the endpoint
that is not 2:

| from vertex 2, follow | the record holds | other endpoint |
| --- | --- | --- |
| `e₁₂` | 1 and 2 | 1 |
| `e₂₃` | 2 and 3 | 3 |
| `e₂₄` | 2 and 4 | 4 |

That gives 1, 3, 4 — the same as `Adj[2]`. The graph has not changed; only the bookkeeping
has.

## Deleting an edge

To delete edge `2–4` from simple neighbor lists, find 4 in vertex 2's list and 2 in vertex
4's. That is a scan, costing `O(deg(2) + deg(4))`.

Do the endpoint pointers in the richer layout fix this? **No.** They say *which* lists
contain the edge, not *where* in those lists its entries sit. Constant-time deletion needs
three more things:

1. **a handle** to `e₂₄` — the record already in hand, not looked up by endpoint names;
2. **back-references** from `e₂₄` to its two entries in the incidence lists;
3. **doubly linked** incidence lists, so an entry you hold can be unlinked by fixing a
   constant number of links.

The edge collection needs the same: save `e₂₄`'s position in it. In an unordered array, move
the last record into the freed slot and update that record's saved index.

## The space is still `Θ(m + n)`

Every addition is a constant amount per vertex or per edge: a record, a few links, two
back-references. So the richer version has the same asymptotic space as the simple one. Do
not read it as an exact count like `n + 5m` — real record sizes depend on the
implementation.

> Fast deletion is not a property of "adjacency lists" in general. It needs a handle to the
> edge and references to *where* it sits in each list, and without those you are scanning.
