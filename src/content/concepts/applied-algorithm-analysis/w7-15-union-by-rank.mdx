`Find` costs one step per parent link, so its worst case is the **height** of the tree:
the most links from any vertex to the root. In the chain `w ⟶ x ⟶ y ⟶ r`, starting at `w`
costs three. A bound on height is therefore a bound on `Find`.

Without a rule, `Union` can build a long chain. Keep putting the old root under a new single
vertex, and after `n` merges you have a path of length `n − 1`, so `Find` is `O(n)`.

## The rule

To merge two groups, make one root point to the other. Each root stores a **rank**, which
starts at 0 for a single vertex.

| Case | Do this | New rank |
| --- | --- | --- |
| ranks differ, `rank(r) = 2`, `rank(q) = 1` | point the **lower**-rank root at the higher: `q ⟶ r` | unchanged: `rank(r) = 2` |
| ranks equal, both 1 | choose either; say `q ⟶ r` | `rank(r)` rises to 2 |

When the ranks differ, the shorter tree goes underneath the taller one without making it any
taller. Only when two equal-rank trees merge can the result be one level taller, so that is
the only case where the rank goes up.

**Rank is not the same as height.** Path compression shortens paths but never lowers a rank,
so a rank can be larger than the tree's current height. Rank is always an *upper bound* on
height, and an upper bound is all the analysis needs.

## A higher rank needs a bigger group

A root's rank increases only when two roots of equal rank merge.

| New root's rank | What must be merged | Fewest vertices |
| --- | --- | --- |
| 0 | one vertex alone | 1 |
| 1 | two rank-0 groups | 1 + 1 = 2 |
| 2 | two rank-1 groups | 2 + 2 = 4 |
| 3 | two rank-2 groups | 4 + 4 = 8 |

Each step up **doubles** the smallest possible group. So a root of rank `r` has at least
`2ʳ` vertices. It can have more, because attaching lower-rank groups adds vertices without
raising the rank.

## From rank to running time

There are only `n` vertices in the whole structure, so

`2ʳ ≤ n` ⇒ `r ≤ log₂ n` ⇒ `height ≤ r ≤ log₂ n`.

| Operation | Cost |
| --- | --- |
| `Find` | follow at most `log₂ n` links: `O(log n)` |
| `Union` | two Finds, then link the roots and update a rank in `O(1)`: `O(log n)` |

For a million vertices, that is at most about 20 links per Find, compared with up to a million
for an unbalanced chain.

Path compression makes later Finds faster still, but the analysis here does not rely on it.
The `O(log n)` bound from union by rank alone is enough for Kruskal's total.

> Rank only increases when two equal-rank groups merge, so rank `r` needs at least `2ʳ`
> vertices. With `n` vertices, rank and height are at most `log₂ n`, and so is the cost of a
> Find.
