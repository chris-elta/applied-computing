Four problems, one method.

## The table

| Problem | Subproblem is indexed by | Time |
| --- | --- | --- |
| Fibonacci | one integer | `O(n)` |
| Shortest path in a dag | a vertex | `O(∣V∣ + ∣E∣)` |
| Longest increasing subsequence | an ending position | `O(n²)`, or `O(n log n)` |
| Edit distance | a pair of prefixes | `O(mn)` |

The middle column is the one that matters. If you can fill it in for a problem you have not
seen before, the recurrence usually follows — because naming what indexes a subproblem is
most of saying what the subproblem is.

## The three steps, every time

1. **Define the subproblem** — a sentence saying what one cell means.
2. **Write the recurrence** — ask what the last decision was.
3. **Choose an order** — base cases first, then any order in which every cell's inputs are
   ready, then read the answer from wherever your definition puts it.

## What sits underneath

- **Overlap** is what separates this from divide and conquer. Subproblems that recur are
  worth storing; independent ones are not.
- **The dag.** Subproblems are nodes, dependencies are edges, and a valid fill order is a
  linearization. Tabulation names the order; memoization discovers it.
- **Cost and solution are different things.** A table gives the cost. Getting the solution
  back means recording decisions (`prev`, `parent`) or keeping enough of the table to
  re-derive them — which is what the two-row memory saving gives up.
