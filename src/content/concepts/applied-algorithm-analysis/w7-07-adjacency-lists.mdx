Prim keeps asking "what are this vertex's neighbours, and what do the edges to them cost?"
The graph needs to be stored so that question is cheap to answer.

## The four towns as lists

For each vertex, keep a list of `(neighbour, weight)` pairs:

```
a: [(b, 1), (c, 4), (d, 3)]
b: [(a, 1), (d, 2)]
c: [(a, 4), (d, 5)]
d: [(a, 3), (b, 2), (c, 5)]
```

In `a`'s list, `(b, 1)` means the edge `(a, b)` with weight 1. Because the graph is
undirected, the same edge also appears as `(a, 1)` in `b`'s list.

**Five edges give ten entries.** Every edge is stored once at each of its endpoints. That is
easy to forget when counting work, and the counts below depend on it.

## What it costs

With `n` vertices, `m` edges, and `d(v)` the number of neighbours of `v`:

| Operation | Cost | Why |
| --- | --- | --- |
| store the graph | `O(n + m)` | `n` lists holding `2m` entries in total |
| scan `v`'s neighbours | `O(d(v))` | read each entry in `v`'s list once |
| scan the whole graph | `O(n + m)` | visit `n` lists and read `2m` entries |

For a connected graph with `n ≥ 2` vertices, `m ≥ n − 1`, since a spanning tree alone needs
that many edges. So `n` is at most `m + 1`, and a full scan is `O(m)`.

## Why scan cost matters

The simplest implementation of Prim finds the cheapest crossing edge by scanning **every**
list each time. For each entry `(w, weight)` in the list of a vertex `v ∈ X`, it checks
whether `w ∉ X` and keeps the smallest weight seen.

The membership check `w ∉ X` has to be cheap, or it would cost more than the scan itself.
Keep a Boolean array `inX[ ]` indexed by vertex: `inX[w]` is true when `w` has joined the
tree. Checking it is `O(1)`.

So one full search for the cheapest crossing edge costs `O(m)`. The next concept counts what
happens when you repeat that search on every pass.

> An undirected edge is stored twice, so the lists hold `2m` entries and a full scan costs
> `O(n + m)`. The running times this week are counted in these scans.
