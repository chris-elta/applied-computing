Iterative DFS made two changes to BFS: a stack, and the mark moved to the pop. It is
tempting to make only the first change and keep marking on push, as BFS does. That search
finds the right vertices. It is not DFS.

## The same graph, two ways

Five vertices `s, a, b, c, d`. Each vertex pushes its neighbors in this order, so the last
one listed ends up on top:

```
s: a, b      a: s, b, c      b: s, d, a
```

**Mark when popped (DFS).** Pop `s` and push `a, b`; `b` is on top. Pop `b`, mark it, push
`s, d, a`. Now `a` is on top — pop it, mark it, and continue from `a`. The search goes from
`s` to `b` to `a` and dives on. Processing order: `s, b, a, c, d`.

**Mark when pushed (not DFS).** Pop `s`; push *and mark* `a` and `b`. Pop `b`. Its neighbors
are `s, d, a` — but `a` was already marked by `s`, so `b` skips it and only `d` goes on.
`a` is reached much later, from `s`. Processing order: `s, b, d, a, c`.

Stand at `b` in each run and ask: *does `b` still have an unexplored neighbor?* Yes — `a`
has not been processed. DFS continues to it. The mark-on-push version goes back to `s`
anyway, because it already decided `a` belonged to `s`. That breaks the rule from the maze
picture: **go back only at a dead end.**

## Why nobody notices

Both versions find all five vertices. A test that only checks *which* vertices are reachable
cannot tell them apart. The difference appears only when something depends on DFS's order —
the tree it builds, or which vertex finishes first. That is precisely what topological sort
depends on, which is why this bug matters.

The recursive version never has this problem: it marks a vertex at the moment a call
arrives there, so no vertex can claim a neighbor in advance.

## The guarantee and the cost

**Same guarantee as BFS.** When DFS ends, a vertex is explored exactly when there is a path
to it from the start, in directed and undirected graphs.

**Recursive cost.** One call per reachable vertex, and each call scans its own list once:
`O(m + n)`.

**Iterative cost.** Each vertex's list is pushed only on its *first* pop — later pops skip.
So the pushes are one for `s` plus one per list entry:

| graph | list entries | most pushes |
| --- | --- | --- |
| undirected | `2m` | `2m + 1` |
| directed | `m` | `m + 1` |

Each push is matched by at most one pop, and both are `O(1)`. On the six-vertex example
with 8 edges, that is `2 · 8 + 1 = 17` pushes. Marking every vertex at the start adds
`O(n)`. Total: **`O(m + n)`**.

> In a stack-based DFS, the mark goes on the pop. Marking on push still finds every vertex,
> but lets one vertex claim another early, so the search turns back before it reaches a dead
> end.
