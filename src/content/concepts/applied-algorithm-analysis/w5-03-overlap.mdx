Weeks 3 and 4 were divide and conquer: split a problem, solve the pieces, combine. Dynamic
programming also splits a problem into smaller ones and combines their answers. So what
makes it a different technique?

Look at what the pieces have to do with each other.

**Mergesort.** The left half and the right half of the array share no elements. Sorting one
tells you nothing about the other, and no subarray is ever sorted twice.

**Fibonacci.** `F(n)` needs `F(n−1)` and `F(n−2)`. But `F(n−1)` *also* needs `F(n−2)`. The
two pieces are not separate problems; one is inside the other.

That is the whole distinction, and it has a name: **overlap**.

| | Divide and conquer | Dynamic programming |
| --- | --- | --- |
| Subproblems are | independent | overlapping |
| Results are | solved separately, then combined | stored and reused |
| Recomputation | none to avoid | avoided by memoization or tabulation |
| Examples | mergesort, quicksort, binary search | Fibonacci, knapsack, shortest paths |
| In one line | divide → solve independently → combine | divide → solve overlapping parts → reuse results |

## Why the storage matters in one and not the other

Storing an answer costs memory and a lookup. That cost is only repaid when the answer is
asked for again. In mergesort it never is, which is why no cache would help it. In Fibonacci
almost every request is a repeat, which is why a cache turns an exponential running time
into a linear one.

So the test for "is this a dynamic programming problem?" is not whether it is recursive —
mergesort is recursive too. It is a practical one: write out the recursion and see whether
the same subproblem appears on more than one branch.

> Overlap is what makes storage pay for itself. Without it you have divide and conquer with
> extra bookkeeping.
