`fib1`'s problem was not recursion. It was **forgetting** — the same subproblem solved over
and over because nothing wrote an answer down.

So write them down. There are two directions to do it in.

## Bottom-up: `fib2`

Start at 0 and work up, keeping your working on the page.

```
function fib2(n)
  if n = 0 return 0
  create an array f[0…n]
  f[0] = 0, f[1] = 1
  for i = 2…n:
    f[i] = f[i−1] + f[i−2]
  return f[n]
```

An **array** is that page of working: numbered boxes, where `f[i]` is the contents of box
`i`. The loop goes in order, so every box it needs is already filled. This is called
**tabulation**.

**Cost:** one addition per box, so about `n` of them. `F(100)` takes 99 additions; `F(200)`
takes 199. Double the input, double the work — that is **linear**, and a different world
from `fib1`.

## Top-down: `fib3`

Keep `fib1`'s shape but give it a notebook (a **memo**) and two habits: check the notebook
before computing, and write to it after. This is **memoisation**.

## Why memoisation is fast — the non-obvious bit

`fib3` makes **the same calls** `fib1` did. The call tree is just as bushy. So why is it
not exponential?

Because almost all those calls now do no work. There are only `n` *different questions* —
`F(0)` through `F(n)` — and each is computed once. Every later call is a lookup.

> Count the **distinct subproblems**, not the calls. That is the core idea of dynamic
> programming, and it returns repeatedly in this course.

## Choosing between them

Same asymptotic cost; different subproblems get solved. `fib2` computes every value whether
needed or not. `fib3` computes only those the recursion reaches — better when the
subproblem space is huge and you touch a scattered few.

Neither is free. `fib2` holds `n` array entries; `fib3` holds a memo **and** a stack `n`
calls deep, which is a real crash risk. We bought linear time with linear memory — and the
next page asks whether we had to.
