Both versions of the multiplication algorithm had the same shape, and so did every other
divide-and-conquer cost this week will meet:

> Solve `a` subproblems of size `n/b`, then combine the answers in `O(nᵈ)` time.

```
T(n) = aT(⌈n/b⌉) + O(nᵈ)
```

Three knobs, and each controls a different feature of the recursion tree:

| knob | meaning | effect on the tree |
| --- | --- | --- |
| `a` | how many subproblems | branching factor — how fast levels widen |
| `b` | how much smaller each is | height, `log_b n` |
| `d` | how expensive the combine step is | cost per node |

For Karatsuba: `a = 3`, `b = 2`, `d = 1`.

## The mistake that costs marks

`d` is the exponent on the work **one call does on its own** — the splitting and the
recombining — *not counting anything its children do*.

That distinction is easy to nod along to and easy to get wrong under pressure. The clean test
is the pair of algorithms you have just seen:

- Four-product version: `a = 4`, `b = 2`, `d = 1` → `O(n²)`
- Karatsuba: `a = 3`, `b = 2`, `d = 1` → `O(n^1.59)`

Both have `d = 1`. Their running times differ. So `d` plainly is not the algorithm's cost —
if it were, the two could not disagree while sharing a value.

The recursive work is already fully accounted for by the `aT(n/b)` term. Counting it again in
`d` double-counts, and every answer comes out wrong.

## Why bother generalising

Module 02 drew one recursion tree by hand and got one answer. This module does the identical
argument with letters instead of numbers — which solves **every** recurrence of that shape at
once, including ones nobody has drawn yet.

The next page states the result and proves it, and the proof is just the Karatsuba tree with
`3` replaced by `a` and `2` replaced by `b`.
