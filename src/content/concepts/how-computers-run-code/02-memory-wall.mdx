Here is the uncomfortable number. A modern CPU executes an instruction in well under a
nanosecond. Fetching a value from main memory takes somewhere around eighty. The
processor can run *hundreds* of instructions in the time it takes one value to arrive.

This gap has a name — the **memory wall** — and it has been widening for thirty years.
Processors got dramatically faster; DRAM latency barely moved. Everything interesting
about modern performance engineering is a response to that one fact.

## What follows from it

Once you accept the gap, a lot of otherwise-strange design decisions snap into focus:

- **Caches** exist to avoid the trip entirely, by keeping recently used data close by.
- **Prefetching** exists to start the trip early, before you ask.
- **Out-of-order execution** exists to find other work to do while you wait.

All three are the same idea wearing different hats: the processor is not trying to go
faster, it is trying to *not be idle*. Which means the question that decides your
program's speed is rarely "how many operations does it do" — it's "how often does it
have to wait".
